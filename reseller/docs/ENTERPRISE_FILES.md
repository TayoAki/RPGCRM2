## How the features are switched on

Three switches control them:

- **`ENTERPRISE_KEY`**: a key signed by Twenty, which you get with an Enterprise subscription. When it's set, the server refreshes a validity token daily from `ENTERPRISE_API_URL` (twenty.com) and reports the seat count. **Without a key, the server never contacts Twenty.**
- **Entitlements**: eight flags that Twenty uses per workspace (`SSO`, `CUSTOM_DOMAIN`, `RLS`, `RECORD_SHARING`, `AUDIT_LOGS`, `USAGE_LIMIT`, `VALIDATION_RULES`, `CUSTOM_ROLES`). With billing off, as in this fork, an entitlement is active only with a valid key. The one exception is `CUSTOM_ROLES`, which is always granted. That's why custom roles work for free.
- **`IS_BILLING_ENABLED`**: turns on Twenty Cloud's Stripe billing. It stays off here.

Some features also sit behind a workspace feature flag. A server admin can flip feature flags. **Don't enable `IS_RECORD_LEVEL_SHARING_ENABLED` without a key**: Twenty ties it to the `RECORD_SHARING` entitlement.

## What runs even without a key

These files are not dormant. The core calls into them on ordinary requests and gets a "feature off" answer back. You can't avoid running them by leaving features off, and deleting them breaks the app. That's why [LICENSING.md](LICENSING.md#enterprise-licensed-code) treats running the free edition commercially as a question to settle with Twenty.

- **Every record read and write.** The workspace repository asks the row-level-permission, record-access-policy (record sharing) and validation-rule code whether anything applies. With the features off, nothing does.
- **Every GraphQL, REST and MCP request.** `ApiRequestContextMiddleware` (usage) attaches the request context used for metering.
- **Every workflow step, logic-function run and email send.** The usage-quota admission check runs and never refuses when billing is off.
- **Workspace load.** Entitlements are resolved by the billing utilities, including the free `CUSTOM_ROLES` grant.
- **Sign-in.** The available-workspaces response type, which includes the list of SSO providers, is an enterprise file.
- **Database schema.** 11 entity files define tables that migrations create in every install: 7 billing tables, SSO identity providers, 2 row-level-permission tables and validation rules. They stay empty.
- **Startup.** `cron:register:all` registers four jobs: key validation, signing-key rotation, audit-log cleanup and app recurring charges. Each one skips without a key or billing.
- **Upgrades.** The `2-4 migrate-to-billing-v2` upgrade command runs with the other upgrade commands.
- **Email campaigns.** The email-group access check and open/click tracking content are enterprise files.

## Feature areas

<a id="billing"></a>
### Subscription billing (Stripe)

Twenty Cloud's own billing: Stripe products, prices, subscriptions and subscription schedules; checkout and the customer portal; trials and their reminder emails; credit grants and metered usage billed per seat or per credit; Stripe webhooks that sync entitlements; and billing for marketplace apps (`app-billing`, recurring charges). It's built around Twenty's plans and needs a key to grant anything. Don't use it to charge your customers. Bill them through your own Stripe account outside the app.

<a id="usage"></a>
### Usage metering and limits

This area tracks consumption per user and per workspace: AI, workflows, apps, storage, API calls, logic functions, emails, webhooks and records. It feeds the usage analytics in settings and enforces credit allowances and caps per day, week or month (`USAGE_LIMIT`). Usage is recorded only when an event sink (ClickHouse analytics) is configured. Caps need the entitlement.

<a id="record-sharing"></a>
### Record sharing

Lets a user share one record with specific people or teams beyond what their role allows. It covers "general access" settings, share invitations, ownership transfer, and objects whose readability is private or inherited. The access-policy part is on the permission path for every record. The sharing UI and mutations need `IS_RECORD_LEVEL_SHARING_ENABLED` plus `RECORD_SHARING`.

<a id="row-level-permissions"></a>
### Row-level permissions

Predicates attached to roles that restrict which records a role sees or edits, such as "owner is me" or "region is EMEA". Admins configure them in Settings → Roles → object permissions. The ORM renders them into SQL filters. The area includes their entities, the workspace-migration builders and runners, the settings UI, and five shared types.

<a id="validation-rules"></a>
### Validation rules

Rules on fields and records that are checked on every create and update. Field and object changes keep them in sync through metadata side effects. They also include their workspace-migration builders and runners. Enforcement needs the `IS_RECORD_CREATION_FORM_ENABLED` feature flag and `VALIDATION_RULES`.

<a id="sso"></a>
### Single sign-on (SAML / OIDC)

Per-workspace identity providers: setup, edit and delete; SAML metadata parsing; OIDC and SAML Passport strategies; the SSO login routes; the provider selection on the sign-in page; and the settings screens. The routes are guarded by `EnterpriseFeaturesEnabledGuard`, which needs a key with a fresh validity token.

<a id="custom-ai-providers"></a>
### Custom AI providers

The admin-panel configuration for your own AI model providers, and the access rule behind it. Access is granted when billing is on, a key is valid, **or the instance has 25 users or fewer** (`MAX_SEATS_WITHOUT_ENTERPRISE_KEY`). This is the one Enterprise feature active by default here. An instance that grows past 25 users loses access without a key.

<a id="enterprise-key"></a>
### Enterprise key validation

Verifies `ENTERPRISE_KEY` (a signed JWT) and stores and refreshes the validity token. It reports seat counts to Twenty, powers the Admin Panel's Enterprise page, and supplies the guard the other areas use. It does nothing without a key.

<a id="audit-logs"></a>
### Audit logs

The audit-log query API, the registry of event types (with the entitlement each one needs), and retention and cleanup. The pipeline that collects events and the live feed are AGPL; only these parts are Enterprise. It needs `AUDIT_LOGS` and an event sink.

<a id="signing-key-rotation"></a>
### Signing-key rotation

A scheduled job that rotates the keys used to sign session tokens. Without a key it skips, so the free edition keeps its signing keys until you rotate them yourself.

<a id="domains"></a>
### Custom domains and email-sending domains

Custom domains per workspace, provisioned through Cloudflare (DNS manager, Cloudflare webhook, settings page; needs `CUSTOM_DOMAIN`). The area also includes the access check for email groups and campaigns, the unsubscribe hostname, and campaign open/click tracking. Campaigns are allowed with the Resend or log email-domain drivers. Other drivers need billing or a key.
